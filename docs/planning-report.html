Dies ersetzt das alte Dossier vollständig

Das vorherige Dossier ging von einem Capacitor-Wrapper (Web-Code bleibt, native Hülle drumherum) mit unverändertem PHP/MySQL-Backend aus, und stellte am Ende zehn offene Fragen. Die Grill-Session hat alle zehn beantwortet — und dabei die Architektur fundamental verändert.

Die vier großen Kurswechsel
  • Wrapper → echter Rewrite. Kein Capacitor, keine WebView. React Native + Expo, komplettes UI neu gebaut.
  • PHP/MySQL/IONOS → Supabase. Kein api.php, kein tmdb.php, kein Cron-PHP mehr für die neue App. Postgres + Auth + Realtime + Edge Functions ersetzen den kompletten Server.
  • „Projekt“-Konzept → nur noch Watch-Gruppen. Die Multi-Tenant-Projekt-Ebene aus der aktuellen Codebase entfällt ersatzlos. Watch-Gruppen sind die einzige teilbare Einheit.
  • Name → WatchCrew. „Filmkritiker Trautmanns“ war zu familienspezifisch für die spätere Marketing-Ambition (andere Familien/Gruppen als zahlende Nutzer, irgendwann).

Was nicht verändert wurde: die funktionale Spezifikation. Was die App können muss — Watchlist, Tagebuch, Bezahl-Tracker, Halbstern-Bewertungen, „Mag ich“, Ähnliche Filme — bleibt exakt wie im Original-Dossier beschrieben. Nur wie es gebaut wird, hat sich komplett geändert. Der Abschnitt „Feature-Inventar“ unten ist entsprechend die alte funktionale Spezifikation, angepasst an die neuen Architektur-Entscheidungen.

Leitplanken für den Rewrite

Drei Grundsätze, die für jeden Milestone gelten — unabhängig davon, wie weit die Implementierung fortschreitet.

01

Die alte Produktions-Datenbank (IONOS/MySQL) wird niemals direkt angefasst. Das alte Backend läuft komplett unangetastet weiter, ausschließlich für die alte App.

02

Die alte PWA bleibt vollständig unangetastet parallel live — als das, was Robin, Tobias und Papa täglich nutzen — bis die neue Supabase-basierte App vollständig verifiziert ist. Kein „wir schalten schon mal ab“, solange nicht wirklich alles läuft.

03

Der Cutover soll downtime-frei sein. Kein Zeitfenster, in dem die Familie die App nicht nutzen kann. Die konkrete Migrationsstrategie (Dual-Write, harter Stichtag-Export o.ä.) wird erst entworfen, wenn diese Phase ansteht — aber das Ziel steht jetzt schon fest.

1 · Architektur

React Native + Expo — echter Rewrite, kein Wrapper

Die zentrale Frage aus dem alten Dossier („Capacitor vs. React Native vs. Flutter“) ist entschieden — und anders, als die vorläufige Empfehlung damals nahelegte.

✓Entschieden: React Native + Expo, TypeScript, Managed Workflow

Volles UI-Rewrite in React Native (Expo, Managed Workflow — nicht Bare), Sprache TypeScript, Paketmanager npm. Kein Capacitor-Wrapper: Robins ursprüngliche „keine native App“-Präferenz wurde in der Grill-Session zugunsten von echtem nativen Feel und einer sauberen Architektur für die spätere Multi-Tenant-Ambition aufgegeben.

Warum RN statt Flutter
Team-Fit: JS/PHP-Hintergrund passt direkt zu React/TypeScript. Marktanteil beider Frameworks ist 2026 eng beieinander (RN leicht vorn bei Enterprise/Jobs, Flutter vorn bei roher Entwickler-Adoption) — kein technisches K.-o.-Kriterium, Team-Fit gab den Ausschlag.
Build-Vorgehen
TDD (Red-Green-Refactor), besonders für Daten-Layer/Hooks/Business-Logik. UI bekommt Component-/Snapshot-Tests obendrauf.
Warum Managed Workflow
Alle gewählten nativen Module (MMKV, Sentry, Supabase, Notifications) haben Config-Plugin-Support — kein Bare Workflow nötig. EAS Build übernimmt Cloud-Builds (zwingend nötig, da kein lokaler Mac für iOS vorhanden ist).
Repo
watchcrew-app — komplett neues Repository, getrennt vom bestehenden filmkritiker-Repo, das unverändert als Live-Deploy der alten App bestehen bleibt.
2 · Backend

Supabase ersetzt PHP/MySQL/IONOS komplett

Die neue App hat keinen traditionellen, immer laufenden Server mehr. Postgres + Auth + Realtime + Edge Functions + pg_cron decken alles Serverseitige ab, Sentry übernimmt ausschließlich Crash-Reporting.

Warum Supabase statt Firebase

Das bestehende Datenmodell ist vollständig relational — Joins, personenbezogene Bewertungen pro Mitglied, Gruppenmitgliedschaften. Das passt zu Postgres, nicht zu Firestores NoSQL-Modell. Zusätzlich liefert Supabase echtes Auth pro Nutzer mit Row Level Security (wichtig für die spätere Multi-Tenant-Ambition) und Realtime für reaktive UI-Updates bei DB-Änderungen — alles aus einer Hand.

Projekte
Zwei Supabase-Projekte, Region Frankfurt/eu-central-1: watchcrew-dev (aktive Entwicklung) und watchcrew-prod (bleibt leer, bis die echte Datenmigration ansteht).
Sicherheits-Default
Beide Projekte: Data API an, „automatisch neue Tabellen exponieren“ aus, Row Level Security automatisch an — secure-by-default, wichtig weil hier später auch fremde Tenants Daten halten könnten.
Was Edge Functions ersetzen
tmdb.php (TMDB/Trakt-Proxy inkl. Cache-Aside), cron-releases.php (jetzt schlanker Release-Reminder-Job via pg_cron), Push-Versand (DB-Webhook → Edge Function → Expo Push API), Linear-Ticket-Erstellung für Feature-Requests.
Secrets
Service-Role-Key und DB-Passwörter verlassen Supabase nie in Richtung Client/EAS — echte Secrets (TMDB/Trakt-Keys, wiederverwendet aus dem alten .env) leben ausschließlich in Supabase Edge Function Secrets, gesetzt per supabase secrets set.
3 · Caching-Strategie

TMDB/Streaming-Daten: Cache-Aside statt Cron-Bulk-Refresh

Löst direkt einen bekannten Bug der alten App: Streaming-Verfügbarkeit wurde bisher nur im Client-Memory ohne echtes TTL gecacht und war dadurch regelmäßig veraltet.

Muster
Server-seitiges Cache-Aside in der TMDB/Trakt-Proxy-Edge-Function: Supabase-Tabelle mit last_fetched_at prüfen — innerhalb TTL → gecachte Zeile zurückgeben (geteilt für die ganze Familie, nicht pro Gerät); veraltet → frisch von TMDB/Trakt holen, Zeile updaten, zurückgeben.
TTL Streaming-Anbieter
24 Stunden. Das war die eigentliche Ursache des „Streaming-Dienste aktualisieren nicht richtig“-Bugs der alten App.
TTL statische Metadaten
Praktisch keins — Laufzeit, Regie, Genres, Poster für bereits erschienene Filme ändern sich nicht. Nur neu laden, wenn ein Feld null ist (wie heute).
Release-Reminder bleibt eigener Job
Kinostart-Push (14/7/1 Tag vorher + Tag selbst) ist inhärent proaktiv, nicht per Lazy-Cache lösbar — bleibt ein schlanker pg_cron + Edge-Function-Job, der aber nur noch anstehende Releasedaten prüft, nicht mehr wie der alte Cron pauschal alles neu lädt.
4 · Datenmodell & Nutzer

Nur noch Watch-Gruppen — die „Projekt“-Ebene entfällt

Die aktuelle Codebase hat sich zu einem Multi-Tenant-„Projekt“-System ausgewachsen (Projekt → Gruppen). Diese Zwischenebene fällt komplett weg. Ein Nutzer kann in mehreren Watch-Gruppen sein — das allein trägt die künftige Mehrfamilien-Ambition.

Rollen
Owner (Ersteller — kann umbenennen, Mitglieder entfernen, Invite-Link regenerieren/widerrufen) und Member (volle App-Nutzung, keine Admin-Rechte). Bewusst keine feinere Rollenstufung für v1.
Beitritt — Weg 1
Wiederverwendbarer Invite-Link (Universal Link über watch-crew.app), kein Ablauf, vom Owner jederzeit widerrufbar/neu generierbar. Primärer Weg, gedacht zum Teilen per WhatsApp.
Beitritt — Weg 2
Manueller „Beitritt per Gruppen-ID“ als Fallback — dieselbe nicht-erratbare UUID wie im Link, keine separate leichter zu erratende ID. Wichtig u. a. zum Reaktivieren einer weich gelöschten leeren Gruppe.
Owner-Übergang
Verlässt der Owner die Gruppe, geht die Rolle automatisch an das am längsten dabei befindliche verbleibende Mitglied — deterministisch, nie manuell auswählbar, Gruppe ist nie ownerlos.
Leere-Gruppe-Aufbewahrung
Verlässt das letzte Mitglied die Gruppe, bleibt sie 2 Wochen reaktivierbar (per Gruppen-ID, mit klarem Warnhinweis beim Verlassen) bevor ein geplanter Job sie endgültig hart löscht.
Kein formales E-Mail-Invite
Für v1 reicht der Link-Invite — ein separates E-Mail-Einladungssystem ist eine mögliche spätere Ergänzung, kein v1-Scope.
5 · Auth

Echte Einzel-Accounts statt geteiltem Projekt-Passwort

Ersetzt die alte „ein Projekt-Passwort, Name aus Dropdown wählen“-UX komplett durch individuelle Supabase-Auth-Accounts.

Methode v1
E-Mail + Passwort. Kein Magic-Link (Robin mag die Extra-Schritt-UX von Einmal-Codes/-Links nicht), kein OAuth. Google (und später Apple, sobald Google Apples verpflichtendes „Sign in with Apple“ triggert) sind spätere Ergänzungen, nicht v1.
E-Mail-Bestätigung
An (Supabase-Default) — schützt vor falsch getippten E-Mails und Zufallsbesuchern über Invite-Links, kleine einmalige Reibung für echte Nutzer.
Konto-Löschung
Pflicht-Feature (App Store Guideline 5.1.1), nicht optional: „Konto löschen“ in den Settings, echte vollständige Löschung, nicht nur Deaktivierung. Komponiert direkt mit der Owner-Übergang-/2-Wochen-Regel aus dem Datenmodell-Abschnitt — keine neue Logik nötig.
Inaktivitäts-Cleanup
Kein Login >1 Jahr (Supabase trackt last_sign_in_at nativ) → Warn-Mail „Konto wird in 14 Tagen gelöscht“ → nach 14 Tagen ohne Login: automatische Löschung. Braucht einen geplanten pg_cron+Edge-Function-Job plus transaktionalen E-Mail-Versand (Supabase-eigenes Auth-Mailing oder Resend — noch nicht final entschieden, bei Implementierung klären).
6 · Realtime & Push

Drei-Wege-Verhalten: still, Toast, oder echte Push

Supabase Realtime ist für v1 im Scope (die anfängliche „erstmal weglassen“-Empfehlung wurde verworfen — der Aufwand ist mit dem Supabase+TanStack-Query-Pairing moderat, nicht „wahnsinnig aufwendig“).

App-ZustandVerhalten
Im Vordergrund, gerade sichtbarer ScreenStilles Live-Update der UI über Supabase Realtime — kein Toast, keine Push.
Im Vordergrund, anderer Screen aktivIn-App-Toast informiert über die Änderung.
Hintergrund oder App geschlossenEchte Push-Notification via Expo Push API, ausgelöst durch einen Supabase-DB-Webhook → Edge Function.

Kein separates FCM/APNs-Wiring nötig, da Expo die Push-Infrastruktur für beide Plattformen übernimmt. Die alten Business-Regeln (Push nur bei Erstbewertung, Deep-Links mit vollem Kontext) bleiben inhaltlich gültig — siehe Feature-Inventar unten.

8 · Admin-Modus

Kein Admin-Modus mehr in der App

Der versteckte „Admin-Modus“ der alten App (TMDB-Bulk-Refresh-Button, Test-Push-Button, Admin-Badge) entfällt komplett — auch nicht in reduzierter Form. Die Idee, wenigstens einen manuellen „TMDB erzwingen“-Button zu behalten, wurde explizit verworfen.

Wohin diese Funktionen wandern

Alle Entwickler-/Betreiber-Fähigkeiten (gruppen-/nutzerübergreifende Übersicht, erzwungene Datenaktualisierung, Löschungen, systemweite Einstellungen) leben künftig in einem separaten, zukünftigen Admin-Backend — einem eigenständigen Web-Tool, das direkt mit Supabase spricht, ausschließlich für Robin als Entwickler. Dieses Dossier behandelt das Admin-Backend nicht. Die mobile App bleibt rein endnutzerorientiert; Owner/Member-Rollen pro Watch-Gruppe sind davon unabhängig und bleiben wie im Datenmodell-Abschnitt definiert.

9 · Branding & Store-Vorbereitung

WatchCrew — Name, Bundle-ID, Domain, Testing

Namensfindung
Zwei frühere Kandidaten — „Reelmates“ und „CineCircle“ — wurden verworfen, nachdem sich zeigte, dass bereits existierende Apps mit nahezu identischem Namen/Konzept live in Google Play/App Store stehen. Lehre für künftige Namensfindungen: immer Store-/Marken-Check vor der Festlegung, nicht danach.
Schreibweise
WatchCrew — zusammengeschrieben, kein Bindestrich, überall außer in der Domain.
Bundle-ID
com.watchcrew.app — reine Eindeutigkeits-Konvention nach Reverse-DNS-Schema, kein echter Domain-Bezug oder -Nachweis nötig.
Domain
watch-crew.app (gekauft, hier mit Bindestrich) — nötig für iOS Universal Links / Android App Links, damit der WhatsApp-geteilte Gruppen-Invite-Link auch bei Leuten ohne installierte App funktioniert (App öffnen falls installiert, sonst Landingpage mit Store-Badges). Ein reines watchcrew://-URL-Schema würde für alle ohne App still fehlschlagen — das würde den zentralen „neue Person einladen“-Anwendungsfall untergraben. Braucht .well-known/apple-app-site-association und assetlinks.json plus eine einfache Fallback-Landingpage.
Repo & Projektnamen
Repo watchcrew-app; Robin benennt auch die Supabase-Dev/Prod-Projekte und das Sentry-Projekt selbst passend zur Marke um (watchcrew-dev/watchcrew-prod).
iOS-Testing
TestFlight Internal Testing — Robins Bruder wird über seine Apple-ID als Team-Mitglied im (kostenpflichtigen) Apple-Developer-Account hinzugefügt. Spart Apples Beta App Review und die umständlichere Ad-Hoc-Distribution (die vorheriges UDID-Registrieren pro Build verlangt).
Datenschutz & AGB
iubenda (EU/DSGVO-fokussiert, passt zum Supabase-Frankfurt/EU-Setup) — eingebundenes, selbst-aktualisierendes Widget statt eines statischen Dokuments, das Robin manuell pflegen müsste. Solide Basis für die bescheidenen Datenkategorien von v1 (E-Mail, Bewertungen, keine Zahlungsdaten); echte Rechtsberatung erst relevant, wenn später wirklich monetarisiert/skaliert wird.
10 · Funktionale Spezifikation

Feature-Inventar

Was die App können muss, bleibt inhaltlich das alte, aus Read-only-Analyse der bestehenden Codebase gewonnene Funktions-Inventar — angepasst an die neuen Architektur-Entscheidungen oben. Grün markierte Einträge sind neu gegenüber der alten App, blau markierte sind inhaltlich angepasst, rot markierte entfallen ersatzlos.

App-Overview

Private Film-Tracking-App für die Familie Trautmann (Robin, Tobias, Dad) — und langfristig für weitere Familien/Gruppen. Nutzer verwalten eine gemeinsame Watchlist, bewerten gesehene Filme (Sterne 0–5 in 0,5-Schritten), führen ein „Bezahl-Tracker“-Rotationssystem für Kinobesuche/Streaming-Abos, und entdecken neue Filme über TMDB-/Trakt-Empfehlungen. Angemeldet per echtem Supabase-Auth-Account (E-Mail+Passwort) statt geteiltem Projekt-Passwort.

Watch-Gruppen mit unabhängigen Watchlists/Tagebüchern/Trackern — für die Familie weiterhin all_three (Robin, Tobias, Dad) und robin_tobias (Robin, Tobias), aber jetzt als generisches, vom Nutzer selbst erstell-/beitretbares Konzept statt fest im Code verankerter Projekt-Gruppen. Gruppenwechsel ändert die komplette sichtbare Datenmenge und die Akzentfarbe der UI (Gold für all_three, Rot für robin_tobias).

3 Tabs für v1 (Bottom-Nav): Tracker · Watchlist · Tagebuch. News-Tab ist für v1 ausgeblendet (siehe „Spätere Phasen“). Dazu Header mit Logo (= Gruppenwechsel), Gruppen-Burger-Menü bei mehreren Gruppen, Settings-Zahnrad. Alle Detail-Overlays, Modals und Formulare laufen über eine gemeinsame Sheet/Modal-Komponente, angetrieben von Expo Router statt eines manuellen Nav-Stacks.

Cross-Cutting Features

Verhaltensweisen, die nicht an einen einzelnen Screen gebunden sind — größtenteils inhaltlich unverändert gültig, mit angepasster technischer Grundlage.

A Auth-Flow angepasst
  • Supabase-Auth-Session statt projektspezifischem Cookie — Token in Expo SecureStore, automatisches Session-Refresh via Supabase-SDK.
  • Analog zur alten iOS-PWA-Lehre („Session darf beim App-Start nicht verloren gehen“): Session wird bei jedem App-Start proaktiv geprüft/erneuert, nicht nur bei aktiver Nutzung — gleiches Prinzip, jetzt über Supabase statt eigenem Cookie-Refresh.
  • Kein DISABLE_AUTH-Escape-Hatch mehr nötig — lokale Entwicklung läuft gegen watchcrew-dev mit echtem Test-Account.
B Push Notifications angepasst
  • Expo Push API statt Web-Push/VAPID; Trigger-Logik (neuer Watchlist-Eintrag, Erstbewertung, Kinostart-Reminder) inhaltlich unverändert, jetzt via Supabase-DB-Webhook → Edge Function ausgelöst.
  • Koexistenz mit Realtime: siehe Drei-Wege-Verhalten im Realtime-Abschnitt oben.
  • Deep-Links tragen weiterhin vollen Kontext (Gruppe+Tab+Film) — jetzt über Expo-Router-Deep-Linking statt ?project=&tab=&group=&movie=-Query-String.
C App-Shell & Offline-Verhalten angepasst
  • Ersetzt die alte PWA-Installierbarkeit (manifest.json/sw.js) — App-Icons/Splash-Screen über Expo-Konfiguration, kein Service Worker mehr.
  • Offline „Stufe 1“ für v1: Read-Cache/graceful degradation über TanStack Query + MMKV-Persistenz. Keine Offline-Mutation-Queue (Stufe 2, bewusst spätere Phase) — Mutationen brauchen weiterhin eine Verbindung.
D „Mag ich“ / Like-Feature +

Unverändert gültig: pro Nutzer unabhängig, setzbar im Rating- und Bearbeiten-Dialog, Löschen einer Bewertung setzt auch das Like zurück, eigener Diary-Filter „Mag ich ♥“.

E Sterne-Rating (0–5, Halbstern) +

Unverändert gültig, inklusive Speicherformat (DECIMAL(2,1), eindeutig pro Watchlist-Eintrag+Mitglied). Struktur unverändert (statische Liste + Versions-Vergleich). Reset auf frisches v1.0.0 — die ~130 historischen Einträge sind web-implementierungsspezifisch und werden nicht migriert.

J Multi-Projekt-System entfällt

Entfällt vollständig — siehe Datenmodell-Abschnitt oben. Watch-Gruppen sind die einzige verbleibende teilbare Einheit, ein Nutzer kann direkt in mehreren sein, ohne eine „Projekt“-Zwischenebene.

State-Management & Caching-Prinzip

Ersetzt die alten globalen let/const-Variablen aus state.js: Server-State (Movies/Ratings) lebt in TanStack Query, aktualisiert nach jeder Mutation UND per Realtime-Event statt durch manuelles Invalidieren+Neuladen. Client-/UI-State (Sort/Filter-Auswahl, temporäre Rating-Werte während offener Dialoge, aktive Gruppe, Feature-Flags) lebt in Zustand. Geräte-Präferenzen, die einen App-Neustart überleben müssen, liegen in MMKV.

Prinzip bleibt — Mechanik wechselt

Die alte Trennung „Server-Daten sind ephemer, Geräte-Präferenzen sind dauerhaft lokal, niemals Filmdaten selbst in localStorage“ bleibt als Prinzip 1:1 gültig — nur dass TanStack Query + Realtime jetzt granularer aktualisieren kann, statt bei jeder Mutation zwingend den kompletten View neu zu laden.

Verhaltens-Constraints aus der Bugfix-Historie

Business-Regeln aus echten vergangenen Bugs — technologieunabhängig, bleiben als bindende Anforderungen für den Rewrite gültig.

paid_atEin bereits gesetztes Zahlungsdatum darf beim Bearbeiten/Bewerten niemals stillschweigend auf „heute“ zurückgesetzt werden, außer es wird explizit ein neues Datum übergeben oder es existierte noch keins.
nav-stackTab-Wechsel muss jeden offenen Modal-Stack vollständig zurücksetzen — bei Expo Router strukturell durch unabhängige Pro-Tab-Stacks gelöst (siehe H oben).
sessionAuth-Session darf bei App-Start nach OS-Kill nicht verloren gehen — Session muss proaktiv bei jedem Start geprüft/erneuert werden.
ui„Mag ich“ gehört als Option ins bestehende Sortier-Dropdown, nicht als zusätzliches UI-Element.
designVisuelle Konsistenz zwischen Karten-Badges und Dialog-Icons (Stern/Herz-Größe) über ein gemeinsames Komponenten-Set lösen, nicht pro Screen neu bauen.
state-initNeue Features dürfen unabhängige Views nicht durch geteilten State beeinflussen; Dialog-State muss beim Öffnen deterministisch aus Serverdaten initialisiert werden.
sonderzeichenFilm-/Personen-/Studionamen können beliebige Sonderzeichen inkl. Apostrophe enthalten — bei deklarativem React-Rendering strukturell unkritisch (kein innerHTML), aber in TDD-Tests explizit mit solchen Namen abdecken.
navbackZurück-Navigation zu einer Einstellungsseite muss deren Anzeige immer aus aktuellem State neu aufbauen, nie aus gefrorenem Snapshot.
cacheCaching-Schicht muss leere/fehlgeschlagene Ergebnisse von echten Treffern unterscheiden und Neuversuche zulassen — gilt direkt für die neue TMDB-Cache-Aside-Tabelle.
payment-uiZahlungs-Zuordnung muss in jedem Bewertungs-/Bearbeitungs-Dialog konsistent vorhanden und korrekt ans Tracker-Feature-Flag gekoppelt sein — über typisierten Component-State lösen, nicht DOM-Query.
likeLike ist pro Nutzer unabhängig; Löschen der Bewertung setzt auch das Like zurück.
filter„Kommt noch“ schließt bereits streambare Filme explizit aus, nicht nur „kein Datum oder Zukunft“.
deep-linkJeder Push-/Realtime-Deep-Link muss vollen Kontext (Gruppe+Tab+Film) tragen, sonst geht der Zielzustand beim Kaltstart verloren.
pushPush/Toast nur bei Erstbewertung, nicht bei nachträglicher Korrektur.
datum„Gesehen am“ (seen_at) und Bewertungs-Timestamp (rated_at) sind bewusst getrennte Felder — nicht zusammenfassen.
personenbezugGesehen-Datum eines Nutzers wird nie durch Aktion eines anderen Nutzers überschrieben.
bewertenBewerten nur für bereits erschienene oder streambare Filme.
datenmodellSingle-Table-Modell bleibt zwingend: Watchlist/Tagebuch sind keine getrennten Datensätze — Übergang ausschließlich über Vorhandensein einer Bewertung. Kein „Verschieben“-Vorgang nachbauen (siehe Leitplanken).
